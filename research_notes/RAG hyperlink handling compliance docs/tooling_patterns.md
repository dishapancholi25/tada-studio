# RAG Ingestion Tooling: Handling of In-Document Hyperlinks

## Do established tools extract hyperlink URLs/anchor text as structured metadata, or just flat text (dropping link structure)?

### Takeaway
Behavior is inconsistent and mostly format-dependent: **Unstructured.io is confirmed (via official docs) to expose structured link fields** (`link_urls`, `link_texts`, `link_start_indexes`, `links`) for HTML and PDF elements. **pdfplumber** exposes a `.hyperlinks` property per page. **PyMuPDF** exposes raw link annotations via `page.get_links()` / `page.links()`. By contrast, **Azure AI Document Intelligence, PyMuPDF4LLM, and (per community reports) LlamaIndex's default PDF loaders either drop link targets entirely or only preserve visible anchor text**, requiring manual post-processing to recover URLs. Docling's actual hyperlink-field behavior in its DoclingDocument schema could not be confirmed from available sources.

### Cited Findings
- Unstructured's official "Document elements and metadata" docs list, as confirmed link-related metadata fields: `link_urls` ("A list of URLs within the extracted content", HTML), `link_texts` (text strings associated with `link_urls`, HTML), `link_start_indexes` (index locations within extracted content where links can be found, HTML and PDF), and `links` ("A list of links within the extracted content", PDF) — [Unstructured document elements docs](https://docs.unstructured.io/open-source/concepts/document-elements)
- It was not possible to confirm from available sources whether `partition_docx` specifically populates these link fields for DOCX files (vs. only HTML/PDF); the official metadata page's docx-specific section discusses heading hierarchy (ilvls) but says nothing about links — [Unstructured document elements docs](https://docs.unstructured.io/open-source/concepts/document-elements), [Unstructured partitioning docs](https://docs.unstructured.io/open-source/core-functionality/partitioning)
- pdfplumber's official README describes a `.hyperlinks` property: each entry corresponds to a PDF annotation of the Link subtype with a URI action (per PDF spec section 8.4) — [pdfplumber README](https://cdn.jsdelivr.net/gh/jsvine/pdfplumber@stable/README.md)
- PyMuPDF's `page.get_links()` returns a list of dictionaries (one per link annotation), with an iterator form `page.links()`; keys include things like `kind`, `xref`, `from`, and `uri`, though the exact field documentation page could not be fully retrieved — [PyMuPDF docs mirror](https://pymupdftest.readthedocs.io/en/stable/tutorial.html), [Gurubase PyMuPDF link tutorial](https://gurubase.io/g/python/extract-page-links-pdf-pymupdf-python)
- A LangChain community source confirms **PyPDFLoader's metadata is limited to `source` (file path) and `page` (page number)** — no link metadata — [Document loaders in LangChain (Medium)](https://medium.com/data-and-beyond/document-loaders-in-langchain-f23d3ce70d66)
- PyMuPDF4LLM (used for PDF→Markdown conversion, relevant to Marker-adjacent pipelines) has hyperlink extraction/preservation **confirmed as unsupported** by a maintainer ("This feature is not yet supported in PyMuPDF4LLM") on the official MuPDF forum, dated discussion. The maintainer noted links can be internal or external, and many link objects are invisible rectangles over page regions rather than visible link text, complicating extraction — [MuPDF forum thread](https://forum.mupdf.com/t/issue-hyperlink-extraction-from-pdf-to-markdown-is-not-working/263)
- Microsoft's own Q&A volunteer moderator (2025-03-14) stated for Azure AI Document Intelligence: "While it can extract text that includes hyperlinks, it does not natively extract or separate the URLs from the hyperlink text in the output," and suggested regex post-processing or a PDF parsing library (e.g., PyPDF2/pypdf) as a workaround, or filing a feature request with Microsoft — [Microsoft Q&A](https://learn.microsoft.com/en-us/answers/a/2002080)
- A separate, more recent Microsoft Q&A thread (dated around November 2025, re: Content Understanding) reportedly got a similar moderator response: OCR reads visible text well, but Azure does not return link annotations embedded inside a PDF, with the same PyMuPDF/pypdf + coordinate-matching workaround suggested — [Microsoft Q&A — Content Understanding links](https://learn.microsoft.com/en-us/answers/questions/5634203/extract-text-and-associated-links-using-content-un)
- An older (2023) Microsoft Q&A thread had a Microsoft moderator stating Form Recognizer (predecessor branding of Document Intelligence) "does not specifically extract hyperlinks" — [Microsoft Q&A](https://learn.microsoft.com/en-us/answers/a/1261764)
- A LlamaIndex community forum report stated that SimpleDirectoryReader and PDF data loaders on LlamaHub "ignore non-text elements, which includes clickable link annotations" by default, pushing the user to write a custom PyMuPDF-based reader instead — source could not be directly fetched (DNS failure on `community.llamaindex.ai`); this finding comes only from a WebSearch snippet summary, not a verified primary-source read, so treat with reduced confidence
- Deepset's `DOCXToDocument` connector (not one of the five target tools, but a comparable DOCX-ingestion component) explicitly supports a "Link Format" option controlling how hyperlinks appear in extracted text: none (text only, default), markdown (`[text](url)`), or plain (`text (url)`) — showing this is a solved, productized problem elsewhere in the ecosystem — [Deepset docs](https://docs.cloud.deepset.ai/docs/docxtodocument)
- ContextGem's DOCX converter similarly has a "links" option that "processes and formats hyperlinks, preserving both link text and target URLs" — [ContextGem docs](https://contextgem.dev/converters/docx)
- Docling (via DataCamp tutorial and PyPI package descriptions) is documented to convert PDFs to structured JSON/Markdown with metadata and layout analysis (DocLayNet, TableFormer), but **no source found explicitly confirms or denies whether hyperlink targets are preserved as a field on text items in the DoclingDocument model** — [DataCamp Docling tutorial](https://www.datacamp.com/de/tutorial/docling), [llama-index-readers-docling PyPI](https://pypi.org/project/llama-index-readers-docling)

### Inferences
- There appears to be a split in the ecosystem: tools built primarily around **HTML/web content** (Unstructured, LangChain's HtmlLinkExtractor) have mature, structured hyperlink metadata, because HTML's `<a href>` tag makes extraction trivial. Tools centered on **PDF** (Azure DI, PyMuPDF4LLM, default LangChain/LlamaIndex PDF loaders) treat hyperlinks as a secondary, often-unsupported feature, likely because PDF link annotations are structurally separate from the text layer (an annotation dictionary with a rectangle, not an inline tag) and require explicit extra extraction code.
- The consistent workaround recommended across Azure, LlamaIndex community, and PyMuPDF4LLM sources — "read the PDF's link annotations yourself via PyMuPDF/pypdf and join them to the text output by position/text-matching" — suggests this is the de facto industry pattern rather than relying on any single framework's built-in support.

### Gaps
- Could not confirm Docling's/docling-core's actual schema field for hyperlinks (e.g., whether `DocItem` or `TextItem` has a `hyperlink` attribute) — searches for "docling_core DocItem hyperlink field schema" returned no Docling-specific results; would require direct inspection of the docling-core GitHub source (`types/doc` module) or installed package, which was not accessible in this research pass.
- Could not directly verify (via a working fetch) whether `partition_docx` in Unstructured actually populates the `link_urls`/`link_texts` fields for DOCX input specifically, as opposed to only HTML and PDF as the docs table implies.
- Could not independently verify the LlamaIndex community forum post content (fetch failed with DNS error); only a search-snippet summary was available.
- No official LlamaIndex release notes or GitHub statement was found confirming or denying built-in hyperlink extraction in current (2025–2026) versions.

## Is there a built-in feature (or common plugin/pattern) for "following"/"crawling" a hyperlink found inside a document and auto-ingesting the linked page?

### Takeaway
**No tool in scope (LangChain, LlamaIndex, Docling, Unstructured.io, Azure AI Document Intelligence) has a built-in feature that detects a hyperlink inside a parsed PDF/DOCX and automatically fetches/ingests the linked page.** LangChain does have a general-purpose web-crawling loader (`RecursiveUrlLoader`) and an HTML-specific link extractor/graph-store pattern, but these operate on HTML pages being crawled directly — not on links discovered as a byproduct of parsing an uploaded PDF/DOCX. Wiring "extract link from PDF → fetch target → ingest" appears to be something practitioners build themselves.

### Cited Findings
- LangChain's `RecursiveUrlLoader` (in `langchain_community.document_loaders`) crawls recursively from a start URL, controlled by `max_depth` (default 2: depth 1 = only the start page, depth 2 = also pages it links to), stays on the same domain by default (`prevent_outside`), supports `link_regex`/`exclude_dirs` filtering, and the official docs explicitly warn of SSRF risk if pointed at internal servers — [LangChain RecursiveUrlLoader docs](https://python.langchain.com/docs/integrations/document_loaders/recursive_url/), [API reference](https://reference.langchain.com/v0.3/python/community/document_loaders/langchain_community.document_loaders.recursive_url_loader.RecursiveUrlLoader.html)
- This loader is designed to start from a URL and crawl its own linked pages — it is not described anywhere in retrieved sources as something that ingests a PDF/DOCX first and then follows links discovered inside that file's content.
- LangChain's `HtmlLinkExtractor` (in `langchain_community.graph_vectorstores.extractors`, marked **beta** — "the API may change") extracts `<a href>` hyperlinks from an HTML string/BeautifulSoup object and attaches them to a Document's metadata via `add_links()`, for use in a `GraphVectorStore` — but this operates on HTML input, not on PDF/DOCX parsed content, and does not itself fetch/ingest the linked page; it only records the link as a traversable edge between already-ingested documents — [LangChain HtmlLinkExtractor API reference](https://python.langchain.com/api_reference/community/graph_vectorstores/langchain_community.graph_vectorstores.extractors.html_link_extractor.HtmlLinkExtractor.html)
- A LlamaIndex PyPI package, `llama-index-readers-remote-depth`, "extract[s] the text from the links available in a webpage URL" with a configurable depth parameter — again a web-page-to-web-page crawler, not a document-embedded-link-to-web-page crawler, and its example uses an older `download_loader` API pattern, suggesting it may not be actively maintained in current form — [llama-index-readers-remote-depth PyPI](https://pypi.org/project/llama-index-readers-remote-depth/0.1.0)
- No source found for Docling, Unstructured.io, or Azure AI Document Intelligence describes any auto-follow/crawl-on-ingest capability for links found inside parsed documents.

### Inferences
- The absence of any "detect link in PDF → auto-fetch → ingest" feature across all five target tools, combined with the existence of separate general-purpose web crawlers (RecursiveUrlLoader) that would need to be manually triggered with URLs pulled out of a document, strongly suggests this is currently a **custom integration practitioners must build themselves**: extract link via PyMuPDF/pdfplumber/Unstructured, then separately invoke a web loader/crawler on the extracted URL list.

### Gaps
- No GitHub issues or discussion threads specifically proposing or tracking a "crawl hyperlinks found in ingested documents" feature were found in this research pass for any of the five tools; a more exhaustive search of each project's GitHub Issues tab (filtered by "hyperlink," "follow link," "crawl") would likely be needed to confirm there is truly no open feature request, but time/tool-call budget did not allow for in-repo issue searches beyond general web search.
- Unclear whether Azure AI Document Intelligence has (or plans) any "linked resource" ingestion feature as part of its broader Azure AI Search / Copilot integration stack; not found in this pass.

## What do official docs, GitHub issues/discussions, or engineering blogs say about recommended patterns for handling cross-references/external links during ingestion?

### Takeaway
The clearest, most concrete documented pattern found is **LangChain's GraphVectorStore + HtmlLinkExtractor design**, which treats hyperlinks as directed graph edges between documents, combining vector similarity search with graph traversal at retrieval time. For PDFs specifically, the consistent advice from Microsoft and community sources is to **extract link annotations with a dedicated PDF library and join them to the OCR/text output using regex or coordinate/position matching** rather than relying on the parsing tool itself.

### Cited Findings
- LangChain's graph vector store design: links are directed and "directionality controls how the graph is traversed at retrieval time"; documents connect to "tags" and tags connect to other documents, such that two documents are considered linked at depth one if they point to the same tag — [LangChain graph_vectorstores reference](https://reference.langchain.com/python/langchain-community/graph_vectorstores)
- A DataStax engineering blog post on GraphRAG describes the general pattern: "vector search finds semantically similar documents, then graph traversal follows relationships like hyperlinks, citations, or references to reach documents that are contextually connected but not semantically similar" — [DataStax GraphRAG by example](https://datastax.com/blog/graphrag-by-example)
- Microsoft's official Q&A guidance (moderator response) for handling links Document Intelligence can't separate: "you can use regular expressions or PDF parsing libraries to extract and combine URLs with the hyperlink text," and if link extraction is a hard requirement, "consider submitting a feature request to Microsoft" — [Microsoft Q&A](https://learn.microsoft.com/en-us/answers/a/2002080)
- The MuPDF forum maintainer's framing of why PDF links are hard to handle generally (applicable as a cross-tool design consideration): links can be **internal** (pointing to another location in the same document, i.e., a true cross-reference) or **external** (pointing to a website), and many link annotations are invisible overlay rectangles rather than aligned with visible anchor text — meaning naive text-to-link alignment by itself is unreliable and a geometry/position-based join is often necessary — [MuPDF forum](https://forum.mupdf.com/t/issue-hyperlink-extraction-from-pdf-to-markdown-is-not-working/263)
- Deepset's and ContextGem's DOCX converters both formalize "render the hyperlink inline as Markdown (`[text](url)`) or as `text (url)`" as the recommended output pattern once links are extracted, rather than dropping the URL or keeping it as a side-channel metadata-only field — [Deepset docs](https://docs.cloud.deepset.ai/docs/docxtodocument), [ContextGem docs](https://contextgem.dev/converters/docx)

### Inferences
- There appear to be two competing philosophies for "handling" links during ingestion: (1) **inline-in-text** (convert the link into Markdown `[anchor](url)` syntax directly in the chunk text, as Deepset/ContextGem do), which keeps the URL visible to the LLM at generation time without special retrieval logic, versus (2) **structured graph-edge** (LangChain's GraphVectorStore approach), which treats the link as a retrieval-time traversal signal rather than embedding it in the text. Teams building a RAG pipeline need to choose based on whether they want the model to see raw URLs in context or want retrieval to traverse references.

### Gaps
- No official blog post or documentation was found specifically from the Docling, Unstructured.io, or LlamaIndex engineering teams discussing design rationale or best practices for cross-reference/external-link handling; what's cited above about general patterns comes from LangChain/DataStax material and from DOCX-converter vendors outside the five-tool core scope.
- Could not find GitHub issue/discussion threads (as opposed to general docs or Q&A) from the Docling or Unstructured.io repos specifically discussing this topic, despite targeted searches; it's possible relevant discussions exist but weren't surfaced by the search tool, rather than confirmed absent.

## Are there known open-source examples/repos implementing hyperlink-aware chunking or graph construction?

### Takeaway
The one concrete, well-documented open-source example found is **LangChain's `graph_vectorstores` module** (specifically `HtmlLinkExtractor` + `add_links()` + `CassandraGraphVectorStore`/compatible graph vector stores), which builds a bipartite document–tag graph from extracted hyperlinks and uses it at retrieval time. Beyond this, most "GraphRAG from PDF" tooling found (FalkorDB GraphRAG SDK, grawiki) builds its graph from **extracted entities/chunks**, not from the document's embedded hyperlinks specifically — a distinct pattern from what was asked about.

### Cited Findings
- LangChain's `HtmlLinkExtractor` + `add_links()` + graph vector store pattern is implemented and documented (beta status) in `langchain_community.graph_vectorstores`, with directed links forming a traversable graph structure at query time — [LangChain graph_vectorstores API](https://python.langchain.com/api_reference/community/graph_vectorstores/langchain_community.graph_vectorstores.extractors.html_link_extractor.HtmlLinkExtractor.html), [reference docs](https://reference.langchain.com/python/langchain-community/graph_vectorstores)
- `KeybertLinkExtractor` is a sibling extractor in the same LangChain module that links documents by shared keywords rather than explicit hyperlinks — presented in the docs as an alternative/complementary technique, confirming the module's general design is extractor-pluggable (hyperlinks are just one "kind" of link) — (same source as above)
- The FalkorDB GraphRAG SDK auto-routes `.pdf` files to a PDF-specific loader and builds a "lexical graph" with `Document` nodes, `Chunk` nodes, `PART_OF` edges, and `NEXT_CHUNK` edges for provenance/traceability — this is a **chunk-sequence and entity graph**, not demonstrated to use in-document hyperlinks as edges — [FalkorDB GraphRAG ingestion docs](https://docs.graphrag.falkordb.com/ingestion)
- `grawiki` converts PDFs to Markdown, then performs chunk-level entity extraction to build graph state — also an entity/chunk graph, not hyperlink-based — [grawiki docs](https://grawiki.readthedocs.io/en/latest/flows/)

### Inferences
- "Hyperlink-aware" graph construction (using the literal hyperlinks embedded in a document as graph edges) appears to be a narrower, less-common pattern than general GraphRAG (which builds graphs from extracted entities/relations via LLM, regardless of whether the source document had hyperlinks). LangChain's graph_vectorstores module is the only clear match found for "use the actual hyperlink as the graph edge," and it is HTML-focused and explicitly beta.

### Gaps
- No PDF/DOCX-specific open-source repo was found that extracts embedded hyperlink annotations and turns them directly into knowledge-graph edges (as opposed to LangChain's HTML-focused `HtmlLinkExtractor`). This may exist as a community notebook/blog implementation not surfaced by the queries used; a more exhaustive GitHub code-search (e.g., for repos combining `PyMuPDF get_links` with a graph database ingestion step) would be needed to rule this out definitively.
- Did not find any Docling- or Unstructured.io-specific community project described as doing hyperlink-aware chunking.
