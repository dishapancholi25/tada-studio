# Graph-Based and Reference-Node Techniques for Representing Hyperlinks/Cross-References in RAG (Alternative to Crawl-vs-Ignore)

## What is GraphRAG (Microsoft) and does it model explicit links/citations as edges?

### Takeaway
Microsoft's GraphRAG builds its graph by having an LLM extract entities and relationships from document text itself (not from the document's native hyperlinks/citations) — it is an entity-relationship graph, not a hyperlink/citation graph. It is also expensive to build and update, which has motivated lighter-weight "implicit"/metadata-based alternatives that are closer to what a hyperlink-as-edge design would look like.

### Cited Findings
- GraphRAG's indexing pipeline uses an LLM to scan chunks and extract entities (people, companies, places, concepts) and the relationships between them; results from chunks are deduplicated/merged into one graph where nodes are entities and edges are relations carrying weights and descriptions — [Medium: Microsoft's GraphRAG: From Local to Global Query Focused Summarisation](https://medium.com/@aiclub.iitm/microsofts-graphrag-from-local-to-global-query-focused-summarisation-8aae7cfa55ce)
- The indexing process also extracts "covariates" such as claims, in addition to entity nodes and relationship edges — [Inside GraphRAG (Medium/Percena)](https://medium.com/percena/inside-graphrag-analyzing-microsofts-innovative-framework-for-knowledge-graph-processing1-6f84deec5499)
- GraphRAG does not require a manually pre-built knowledge graph — entities/relationships come purely from LLM extraction over unstructured text, not from the document's own hyperlink/citation markup — [Inside GraphRAG (Medium/Percena)](https://medium.com/percena/inside-graphrag-analyzing-microsofts-innovative-framework-for-knowledge-graph-processing1-6f84deec5499)
- After graph construction, the Leiden community-detection algorithm partitions the graph into modular communities, and an LLM generates bottom-up summaries per community; retrieval splits into "Local Search" (precise factual queries) vs. "Global Search" (corpus-wide thematic queries, run in parallel across communities and summarized) — [Medium: GraphRAG local-to-global](https://medium.com/@aiclub.iitm/microsofts-graphrag-from-local-to-global-query-focused-summarisation-8aae7cfa55ce)
- Indexing cost is high because the LLM must process every chunk to extract entities/relations/claims — described as "the price" for better performance on broad, corpus-wide questions — [machinelearningatscale.com design-pattern post](https://www.machinelearningatscale.com/blog/graphrag-knowledge-graph-retrieval)
- A direct critique of the GraphRAG design, from Contextual AI, argues GraphRAG "precomputes a static graph of nodes and edges using rigid heuristics for edge construction, deduplication, and traversal" ("heuristic overload"), that updates are costly because community detection/hierarchical summaries can force recomputation across much of the graph when a single document changes, and that in their own ablations, complex steps like community summarization gave diminishing returns relative to cost/latency — [Contextual AI: An Agentic Alternative to GraphRAG](https://contextual.ai/blog/an-agentic-alternative-to-graphrag)

### Inferences
- GraphRAG as published is not itself a technique for modeling a document's *own* hyperlinks/cross-references as edges — its graph edges are LLM-inferred semantic relationships between extracted entities, built regardless of whether the source text contains literal hyperlinks. It is relevant to this research mainly as a contrast case: a heavier, fully-precomputed graph-construction paradigm, against which lighter "treat the reference as metadata, resolve at query time" approaches (see Key Question 2) are explicitly positioned as cheaper alternatives.
- For bank policy documents with explicit "see also"/cross-reference style links, a GraphRAG-style LLM-entity-extraction pass would need to be paired with (or replaced by) an explicit pass that parses the document's actual hyperlink/citation markup, since GraphRAG's extraction does not inherently special-case hyperlinks.

### Gaps
- I could not confirm the exact title/arXiv link of the original Microsoft Research GraphRAG paper (Edge et al., 2024) from search results; sources describe it but did not surface a direct primary-source link in this session.
- No source found describing a GraphRAG variant that explicitly ingests a document's native hyperlink/citation structure as seed edges (as opposed to LLM-inferred entity relations) — this appears to be outside GraphRAG's documented design as covered by available sources.

## Are there documented patterns for storing a hyperlink as a "reference node" (target identifier, anchor text, source chunk, context) retrievable without crawling the target's full content?

### Takeaway
Yes — multiple documented patterns exist for treating a hyperlink/cross-reference as a lightweight, retrievable pointer rather than crawled content: (1) DataStax's RAGStack "Knowledge/Graph Store" models hyperlinks as explicit `Links` metadata attached to a document/chunk, used to connect nodes without necessarily fetching target content; (2) Contextual AI's "agentic" approach stores cross-reference pointers (e.g., "Section 4.2.1") in a separate searchable "aliases" metadata index that the agent queries only when it decides a reference matters, without precomputing a graph at all; (3) a 2026 arXiv paper (LARAG) proposes encoding hyperlink relations as chunk metadata specifically to avoid maintaining a separate graph representation.

### Cited Findings
- DataStax RAGStack's graph/knowledge store attaches a `links` metadata field to each `Document`/node ("a set of Links indicating how this node should be linked to other nodes"); for HTML content, an `HtmlLinkExtractor` class extracts links from raw HTML (and a `source_url`) via `extract_one(...)` and attaches them via `add_links` — the extractor works on HTML you already supply as a string/BeautifulSoup object; the source material did not state that it fetches/crawls the linked pages itself — [DataStax ragstack-ai-knowledge-store README via GitHub](https://github.com/datastax/ragstack-ai/blob/main/libs/knowledge-store/README.md)
- Each document in this store also carries a `content_id` used to uniquely identify it so re-ingestion overwrites rather than duplicates — [DataStax ragstack-ai-knowledge-store README](https://github.com/datastax/ragstack-ai/blob/main/libs/knowledge-store/README.md)
- Retrieval traversal depth is a parameter: `graph_store.as_retriever(k=4, depth=1)` — depth 0 is vector-only (no edge traversal), depth 1 runs a vector search plus one level of edge traversal; the exact `Link` object schema (e.g., kind/direction/tag fields) was not confirmed from available documentation excerpts — [DataStax ragstack-ai-knowledge-store README](https://github.com/datastax/ragstack-ai/blob/main/libs/knowledge-store/README.md)
- Contextual AI's agentic alternative: at indexing time, a secondary "aliases" index is built per chunk via LLM-prompted metadata extraction — aliases can include section hierarchies, claim lists, citation keys, entities, or questions a chunk answers (e.g., a policy chunk stored under its raw text AND under an alias like "Section 4.2.1"). A separate "Metadata Search Tool" queries this aliases index, distinct from the tool that searches raw content — [Contextual AI: An Agentic Alternative to GraphRAG](https://contextual.ai/blog/an-agentic-alternative-to-graphrag)
- In that design, when semantic search surfaces a chunk containing a pointer like "Refer to Section 4.2.1 for policy details," and the target doesn't match the user's query well enough to surface on its own, the agent recognizes the pointer and explicitly runs a metadata lookup for "Section 4.2.1" against the aliases index — traversal is agent-decided per query, not precomputed — [Contextual AI: An Agentic Alternative to GraphRAG](https://contextual.ai/blog/an-agentic-alternative-to-graphrag)
- The same source distinguishes explicit references (legal/scholarly citations the agent extracts and metadata-searches to jump to the cited chunk) from implicit references (shared entities as metadata enabling multi-hop connections with no shared keywords) — [Contextual AI: An Agentic Alternative to GraphRAG](https://contextual.ai/blog/an-agentic-alternative-to-graphrag)
- On a custom compliance benchmark (Claude Sonnet 4.5), the metadata-tool agent beat content-only retrieval: 75.43% vs. 67.81% accuracy under a 5-turn limit; under a 10-turn limit, content-only reached 80.58% vs. 81.85% for the metadata agent, which also used fewer tool calls, tokens, and lower latency — [Contextual AI: An Agentic Alternative to GraphRAG](https://contextual.ai/blog/an-agentic-alternative-to-graphrag)
- A 2026 arXiv paper, "LARAG: Link-Aware Retrieval Strategy for RAG Systems in Hyperlinked Technical Documentation" (arXiv 2605.07517), is explicitly framed around retrieval over hyperlinked technical documentation; its bibliography cites Microsoft GraphRAG and LangChain GraphRAG as related work, framing itself as an alternative — [arXiv 2605.07517 (LARAG)](https://arxiv.org/pdf/2605.07517)
- A separate summary (from an earlier search pass) described LARAG's approach as encoding "hyperlink relations as metadata associated with each chunk, enabling the retriever to access the author-defined structure of the documentation without maintaining a separate graph representation" — flagged here as a secondhand/aggregator characterization since the PDF body text itself could not be extracted in this session (see Gaps) — [arXiv 2605.07517 (LARAG), PDF](https://arxiv.org/pdf/2605.07517)
- A USPTO patent document describes the base HTML mechanism this all builds on: an anchor element carries an `href` attribute specifying the reference target, and the anchor body (the visible clickable text) is the "citation"/anchor text, which "need not be a human-readable reference... but may be any text, image, and/or other content" — [USPTO Patent 9,529,903](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/9529903)

### Inferences
- The common thread across these sources is: store the reference (anchor text + target identifier + source location) as searchable metadata or a typed edge, and defer any deeper fetch/expansion decision to query time — either via explicit graph traversal with a depth parameter (DataStax) or via an LLM agent explicitly choosing to "follow" the pointer only when the main semantic match is insufficient (Contextual AI). This directly answers the user's framing: it is a documented, named alternative to a binary crawl/ignore decision.
- For a bank policy corpus, the Contextual AI aliases pattern maps cleanly onto "Section X.Y", "Clause N", "Annex A" style internal cross-references, while the DataStax `Links`/edge pattern maps better onto literal hyperlinks to external authority documents (SWIFT, FATF, CBUAE) where the "target" may be an external URL/document ID rather than an internal chunk.

### Gaps
- I was not able to extract the body text of the LARAG paper (PDF text was compressed/non-extractable via WebFetch), so I cannot independently confirm its exact data structure/schema for link metadata, or verify the secondhand summary characterizing it as metadata-only (vs. partial graph). This should be treated as a lower-confidence secondary characterization, not a confirmed primary-source finding.
- The exact field-level schema of DataStax's `Link` object (e.g., whether it records "kind" like `hyperlink` vs. `img`, and directionality) was not available in the fetched README excerpt — would need the source code or a fuller doc page to confirm.
- No source found specifying whether/how either pattern records the *surrounding context* (the sentence/paragraph around the anchor) as a distinct stored field vs. just relying on the source chunk's own text — this is implied but not explicitly confirmed in the retrieved material.

## How do citation/reference graphs work in legal/academic RAG, and is there a transferable pattern for bank policy docs referencing SWIFT/FATF/CBUAE?

### Takeaway
Multiple recent (2025–2026) legal/regulatory RAG systems explicitly build citation/reference graphs (often in Neo4j) that connect legal provisions, cases, or standards via "cites," "amends," or "shares-principle" edges, generally paired with hybrid (vector + graph) retrieval and an LLM or router deciding when to traverse the graph — this is a directly transferable pattern for a bank policy corpus referencing SWIFT/FATF/CBUAE, though reported results are mixed and mostly self-evaluated/unreplicated.

### Cited Findings
- An Indian legal research assistant (arXiv 2602.23371) builds a Neo4j legal knowledge graph and uses an LLM-based router to decide when to run graph traversal vs. plain retrieval; in an LLM-as-judge evaluation, the hybrid approach reached a 70% pass rate vs. 37.5% for RAG-only — reported as self-evaluated, not independently verified — [arXiv 2602.23371](https://arxiv.org/pdf/2602.23371)
- A New Mexico legal-RAG system (arXiv 2502.20364) pairs vector search with a Neo4j graph whose edges include citations and shared legal principles, plus hierarchical NMF topic clustering feeding the graph as semantic anchors — [arXiv 2502.20364](https://arxiv.org/pdf/2502.20364v2)
- "LEGRA," a graph-based dataset/RAG approach over Polish court rulings (Preprints.org, DOI 10.20944/preprints202511.1742.v1), combines chunking with TF-IDF and embedding enrichment on top of a graph structure, motivated by the claim that text-only search misses relational context between documents — [Preprints.org DOI 10.20944/preprints202511.1742.v1](https://prereview.org/preprints/doi-10.20944-preprints202511.1742.v1/write-a-prereview)
- A COLIEE 2026 Task 1 case-law retrieval entry combines BM25 over citation-context windows, neural reranking, graph features from entity communities, a graph attention network, and a LightGBM meta-learner; its official test F1 (0.177) was far below cross-validation F1 (0.311), attributed by the authors to a recall ceiling, temporal shift, and threshold miscalibration — cited here as an explicit caution that citation-graph features do not automatically generalize to held-out/production data — [papers.cool 2609.26237](https://papers.cool/arxiv/2609.26237)
- Dike (vendor/commercial legal-tech blog) describes treating a citation graph as first-class structure so that an agent asking for a statute article gets the current version, a flag if the article was amended/repealed, and links to interpreting case law — explicitly a vendor claim, not an independent evaluation — [Dike: Why RAG Isn't Enough for Law](https://dike.it.com/blog/why-rag-isnt-enough-for-law)
- A practitioner write-up on U.S. federal regulations (Google Developer forum) argues flat vector stores struggle with the CFR's nested hierarchy and dense cross-references, and built a gold set of 20 multi-hop/temporal-conflict questions to test this — no published benchmark numbers in the available excerpt — [Beyond Semantic Search: Building Agentic Knowledge Graphs for Complex Enterprise RAG](https://discuss.google.dev/t/beyond-semantic-search-building-agentic-knowledge-graphs-for-complex-enterprise-rag/343898)
- A demo system (kuldeepmishra3-legal-rag) combines hybrid vector+BM25 retrieval (reciprocal rank fusion) with GraphRAG over a Neo4j citation graph, answering questions like "which documents cite Act X / case Y"; self-reports a 100-query golden-set evaluation claiming 100% grounded answers across Acts, judgments, and tax documents — self-reported, unreplicated — [Legal RAG demo](https://kuldeepmishra3-legal-rag.hf.space/)
- A 2025 Graph-RAG study on regulatory/technical standards documents (GOST-style technical standards, published in Tomsk State University of Control Systems and Radioelectronics journal) pre-annotated its corpus "for the presence of cross-references within and between documents" and reported Graph-RAG outperforming its closest competitor (Qwen3 + HyDE) by 16.8 percentage points in exact-match accuracy and 10.3 points in factual consistency (p < 0.001, n = 300 queries); the abstract/landing page did not specify the node/edge schema or whether cross-referenced documents are fully indexed vs. referenced as lightweight edges, and it did not report a vanilla-RAG baseline score for comparison — [TUSUR journal: Graph-RAG hybrid retrieval for regulatory/technical documents](https://journal.tusur.ru/en/archive/4-2025/graph-rag-a-hybrid-graph-based-retrieval-for-completeness-and-consistency-in-regulatory-and-technical-document-analysis)
- "RAGulating Compliance: A Multi-Agent Knowledge Graph for Regulatory QA" (arXiv 2508.09893) builds what it calls an "Ontology Free Knowledge Graph" for regulatory QA, with sections on "Sampling and Ground Truth Construction," "System Inference and Evaluations," and "Retrieved Subgraph Visualization" per its document outline; a prior secondhand search summary (not independently verified from body text) described it as extracting subject-predicate-object (SPO) triplets from regulatory documents and embedding triplets alongside source text — body text could not be extracted via WebFetch in this session, so triplet-extraction and edge-typing details remain unconfirmed from primary source — [arXiv 2508.09893](https://arxiv.org/pdf/2508.09893)
- A 2025 finance-data paper proposing FactRAG/HybridRAG reports a 6% reduction in hallucinations and an 80% decrease in token usage vs. conventional RAG in financial/regulatory retrieval contexts — closest match found to AML/finance-regulatory graph-RAG, though not specific to FATF — [preview.aclanthology.org/setup/2025.genaik-1.6](https://preview.aclanthology.org/setup/2025.genaik-1.6)
- An arXiv paper on requirement traceability/compliance checks argues cross-referencing is naturally a graph problem since "requirements often reference interconnected standards, regulations, and supporting documentation" — [arXiv 2412.08593](https://arxiv.org/pdf/2412.08593)

### Inferences
- The dominant transferable pattern across legal/regulatory RAG work is: hybrid retrieval (vector + keyword/BM25) + a citation/cross-reference graph (commonly Neo4j) with typed edges (e.g., "cites," "amends," "shares-principle," "refers-to") + an LLM or router component deciding when to traverse vs. stay in flat retrieval. This is directly applicable to bank policy documents that reference SWIFT/FATF/CBUAE: each reference could become a typed edge (e.g., `REFERENCES`, `IMPLEMENTS`, `SUPERSEDES`) from a policy-document node to either (a) another internal policy node, or (b) an "external authority" placeholder node that stores only the citation identifier/title/anchor text — without requiring the full external standard to be crawled/indexed, mirroring the reference-node pattern from Key Question 2.
- The COLIEE result (test F1 far below cross-validation) and the lack of a vanilla-RAG baseline in the GOST study are useful counter-evidence: citation-graph features demonstrably help in some controlled evaluations but do not reliably generalize, and most reported gains in this space are self-evaluated or benchmarked against another non-trivial baseline rather than a plain-RAG floor. Any production design should budget for its own evaluation rather than assuming a graph layer will automatically outperform flat retrieval.
- No source specifically addressed FATF/SWIFT/CBUAE cross-referencing; the pattern described here is extrapolated from structurally similar legal/regulatory-citation work (CFR, GOST standards, case law), not confirmed against banking-specific sources.

### Gaps
- No FATF-specific, SWIFT-specific, or CBUAE-specific published guidance or schema was found for modeling "see also"/cross-reference relations in a RAG/graph system — this is an extrapolation from adjacent legal/technical-standards work, not a directly confirmed pattern.
- Could not confirm the node/edge schema or crawl-vs-pointer design of the GOST technical-standards Graph-RAG study (journal.tusur.ru) or RAGulating Compliance (arXiv 2508.09893) from primary source text — PDF/body text was not extractable via WebFetch in this session; only abstracts/metadata/document outlines were available.
- No independent (non-self-reported) benchmark comparing citation-graph RAG vs. plain RAG head-to-head within a single legal/regulatory corpus was found.

## What graph-database/property-graph patterns (e.g., Neo4j, LlamaIndex PropertyGraphIndex) are used, and how does retrieval "pull in" a linked node only when relevant?

### Takeaway
LlamaIndex's `PropertyGraphIndex` offers a documented, concrete pattern: build relations either from existing document structure (no LLM needed) or via a schema-constrained LLM extractor, store them as metadata on chunks/nodes, and at query time run a vector search for seed nodes followed by a bounded-depth (`path_depth`) traversal of connected paths — this gives the "pull in a neighbor only when relevant" behavior the user is asking about, since expansion is anchored to vector-similarity hits rather than a blanket graph walk.

### Cited Findings
- `PropertyGraphIndex` construction runs one or more `kg_extractors` over each chunk; results (entities/relations) are stored as metadata on each node; multiple extractors can be combined and are all applied — [LlamaIndex: Using a Property Graph Index](https://docs.llamaindex.ai/en/latest/module_guides/indexing/lpg_index_guide)
- `ImplicitPathExtractor` builds relations purely from existing structure already present on node objects (it reads `node.relationships`) and needs no LLM or embedding model — [LlamaIndex: Using a Property Graph Index](https://docs.llamaindex.ai/en/latest/module_guides/indexing/lpg_index_guide)
- `SchemaLLMPathExtractor` uses an LLM but restricts output to a declared schema of allowed entity types and relation types (e.g., entity types as a `Literal["PERSON", "PLACE", "ORGANIZATION"]`), with Pydantic-based structured-output validation of each extracted path — [Mistral cookbook reproducing LlamaIndex docs](https://docs.mistral.ai/cookbook/third_party-llamaindex-propertygraphs-property_graph_extractors_retrievers)
- Basic construction is via `PropertyGraphIndex.from_documents(...)` with an `llm` and `embed_model`, with separate logged steps for "Extracting paths from text" and "Extracting implicit paths" — [LlamaIndex: Property Graph Index basic example](https://docs.llamaindex.ai/en/latest/examples/property_graph/property_graph_basic)
- Retrieval depth is controlled by a `path_depth` parameter on property-graph retrievers, described as "the number of relation hops to follow after node retrieval" — i.e., expansion happens only *after* an initial node is found, not as a standalone full-graph query — [LlamaIndex: Using a Property Graph Index](https://docs.llamaindex.ai/en/latest/module_guides/indexing/lpg_index_guide) / example setting `path_depth=1` with `similarity_top_k=2` on a `VectorContextRetriever` — [Mistral cookbook](https://docs.mistral.ai/cookbooks/third_party-llamaindex-propertygraphs-property_graph_extractors_retrievers)
- The default `VectorContextRetriever` first finds nodes by embedding similarity, then pulls in the paths connected to those specific nodes (not the whole graph); if the underlying graph store lacks native vector-query support, a separate vector store (default: in-memory `SimpleVectorStore`) is used alongside it — [LlamaIndex: Using a Property Graph Index](https://docs.llamaindex.ai/en/latest/module_guides/indexing/lpg_index_guide)
- A synonym-based retriever variant also takes `path_depth` plus a `max_keywords` setting, used as a sub-retriever alongside the vector-based one — [Mistral cookbook](https://docs.mistral.ai/cookbooks/third_party-llamaindex-propertygraphs-property_graph_extractors_retrievers)
- For explicit multi-hop traversal, Cypher queries can traverse multiple relationships through complex graph patterns — but the default `SimplePropertyGraphStore` (in-memory, no external DB) does not support Cypher; a real graph database (e.g., Neo4j) is needed for that — [LlamaIndex blog: Introducing the Property Graph Index](https://llamaindex.ai/blog/introducing-the-property-graph-index-a-powerful-new-way-to-build-knowledge-graphs-with-llms) / [Mistral cookbook caveat](https://docs.mistral.ai/cookbooks/third_party-llamaindex-propertygraphs-property_graph_extractors_retrievers)
- The older/legacy `KnowledgeGraphIndex` (pre-PropertyGraphIndex) retriever instead works over extracted "knowledge triplets" with traversal fixed at max depth 2 in its documented example, rather than an adjustable `path_depth` — [LlamaIndex Knowledge Graph Demo docs](https://llamaindexxx.readthedocs.io/en/latest/examples/index_structs/knowledge_graph/KnowledgeGraphDemo.html)
- Neo4j's own open-source GraphRAG project converts chunks into a graph where entities, relationships, and contextual links are explicitly modeled; a described benchmark setup used a `HybridCypherRetriever` combining vector search with graph traversal (vector retrieval followed by graph expansion) — [pub.towardsai.net Neo4j GraphRAG writeup](https://pub.towardsai.net/neo4j-needs-just-1-hop-to-answer-what-your-llm-was-guessing-cac8aa6b1e4b)
- A commonly cited chunk-level graph pattern uses `MENTIONS` edges from chunk nodes to entity nodes, with entities connected to each other via `RELATES_TO` edges — [search-aggregated summary of Neo4j GraphRAG patterns, no single primary source isolated]
- DataStax's RAGStack knowledge/graph store (covered in Key Question 2) is a second concrete, documented property-graph-adjacent pattern specifically for hyperlink edges, with a tunable retrieval `depth` parameter (0 = vector-only, 1 = vector + one hop) — [DataStax ragstack-ai-knowledge-store README](https://github.com/datastax/ragstack-ai/blob/main/libs/knowledge-store/README.md)

### Inferences
- A practical design synthesized from these sources for bank policy cross-references: `(:Chunk {id, text, embedding, docId})` nodes; `(:Chunk)-[:REFERENCES {anchorText, targetId}]->(:Chunk|:ExternalAuthority)` edges built via an `ImplicitPathExtractor`-style pass over parsed hyperlink/citation markup (no LLM needed, since the link already exists structurally in the document) rather than an LLM-inference pass; optionally `(:Chunk)-[:MENTIONS]->(:Entity)` edges for topical traversal. At query time: run vector search for seed chunks, then expand 1 hop along `REFERENCES` (matching LlamaIndex's `path_depth=1` / DataStax's `depth=1` pattern) so a linked/cited node is pulled in only when it is structurally adjacent to an already-relevant hit — this is the mechanism that answers "can a query pull in a neighboring linked node only when relevant" affirmatively and concretely.
- Across both LlamaIndex and DataStax, "relevance-gated" expansion is implemented the same way: anchor expansion to vector-similarity hits first, then bound the blast radius with a small integer depth/hop parameter, rather than doing an unconditional full-graph traversal or an unconditional full-content crawl. This is the structural answer to the user's core question of a middle ground between "crawl" and "ignore."

### Gaps
- No source gave the exact field-level schema of a Neo4j "Link"/citation edge type used in production legal-RAG systems (property names, directionality conventions) — only the general `MENTIONS`/`RELATES_TO` pattern and `HybridCypherRetriever` concept were documented in available sources.
- Could not confirm from primary source whether Neo4j's GraphRAG project or the `HybridCypherRetriever` natively supports a "stop traversal if target not embedded/indexed" mode (i.e., truly skipping full-content indexing of the linked node) — available sources describe hybrid vector+graph retrieval generally but didn't address this specific no-crawl nuance for Neo4j specifically (DataStax and LlamaIndex sources did address it more directly, per above).
