# Store the pointer, don't crawl the page

For TADA Studio's 114-document sanctions/compliance corpus, the evidence points away from both naive options the team is weighing: **Option 2 (crawl and index every hyperlink at ingestion time) is a documented anti-pattern** that reproduces known crawler-trap, SSRF, and staleness failures in a bank's own network, while **Option 1 (citation-only, user manually follows the link) fails the audit/provenance bar** that compliance RAG literature treats as non-negotiable. The empirically-supported middle ground is a **reference-node/graph pattern**: parse each hyperlink's URL, anchor text, and surrounding chunk into structured metadata at ingestion time, store it as a lightweight pointer (not fetched content), and defer any actual fetch — of a small, allowlisted set of authoritative domains only — to query time or a separately governed, rate-limited reconciliation job. This pattern is independently implemented in LangChain's `GraphVectorStore`/`HtmlLinkExtractor`, LlamaIndex's `PropertyGraphIndex`, DataStax's RAGStack knowledge store, and described explicitly in a 2026 paper (LARAG) built for exactly this "hyperlinked technical documentation" scenario. The tooling reality for Mashreq's actual 108 PDF / 5 DOCX / 1 PPTX mix complicates execution, however: PDF link-annotation extraction is inconsistently supported across mainstream parsers, so the team should budget for a dedicated extraction step (PyMuPDF/pdfplumber) rather than assuming Azure Document Intelligence or default LangChain/LlamaIndex PDF loaders will surface link targets out of the box. Separately, if any fetching of external content is implemented at all — even narrowly — the pipeline must be built to OWASP's SSRF-prevention standard (allowlist plus post-DNS IP validation plus no auto-redirect-following) given that this exact vulnerability class (CVE-2023-46229, CVE-2024-0243, CVE-2026-27795) has already been found and exploited in mainstream RAG URL-loader code.

## Unbounded crawling is a known failure mode, not an edge case

Recursive link-following without hard bounds is one of the oldest, best-characterized failure modes in crawler engineering, and nothing about a bank's document corpus makes it safer. Production crawlers converge on the same three guardrails — depth limits, visited-set deduplication, and domain allowlisting — specifically because omitting them is the exact configuration known to cause runaway crawls and "crawler traps": combinatorial filter/redirect URLs that generate unbounded duplicate pages, or deliberately adversarial tarpits like the open-source "Nepenthes" project built to trap bots in infinite self-referential link mazes ([MarketingTracer](https://marketingtracer.com/seo/crawler-traps); [404 Media](https://www.404media.co/developer-creates-infinite-maze-to-trap-ai-crawlers-in/)). Mature tools like Scrapy ship `DEPTH_LIMIT`, `allowed_domains`/`OffsiteMiddleware`, and pluggable dedup filters as baseline configuration, not advanced options ([Scrapy docs](https://docs.scrapy.org/en/1.8/topics/spider-middleware.html)), and enterprise connector products (Glean, Elastic, Algolia, Oracle, Sitecore) all implement the same allowlist-plus-depth-cap combination as their standard crawl-scope control, typically capping link-following at **1–3 hops** ([Oracle SES docs](https://docs.oracle.com/cd/E28271_01/apirefs.1111/e23428/objects002.htm); [Sitecore Search docs](https://doc.sitecore.com/search/en/users/search-user-guide/configure-crawler-settings.html)). Microsoft's own (older) Search Server documentation is blunt about the consequence of skipping this: on a highly interconnected site, crawling beyond roughly three hops "can end up crawling most of the internet" ([Microsoft TechNet](https://technet.microsoft.com/en-us/library/cc160648.aspx)). For a sanctions/compliance corpus whose documents cite SWIFT standards pages, FATF, and other regulator sites — each of which links onward to further regulatory and vendor content — unbounded recursive ingestion at Option 2's scale would not stay within the 114-document corpus; it would pull in an open-ended, uncontrolled slice of the external internet, with no natural stopping point.

Layered on top of the scale problem is a security problem specific to a bank's network posture. A backend service that automatically fetches arbitrary URLs discovered inside semi-trusted documents is, per OWASP, a textbook **SSRF (server-side request forgery)** attack surface: if the fetcher does not validate the resolved destination IP (not just the hostname string) before connecting, an attacker who can influence a document's link content — or compromise a linked page that gets re-scraped — can redirect the ingestion host toward internal admin endpoints, cloud metadata services, or other systems reachable from the ingestion host's network segment ([OWASP SSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)). This is not a hypothetical risk invented for this report: it is the documented root cause of the 2019 **Capital One breach** (100M+ customer records exposed via a single forged request to a cloud metadata endpoint) ([Dark Reading](https://www.darkreading.com/cloud-security/analysis-of-jira-bug-stresses-impact-of-ssrf-in-public-cloud)), and it has recurred specifically inside RAG tooling: **CVE-2023-46229** (CVSS 8.8) and **CVE-2024-0243** both affected LangChain's `RecursiveUrlLoader`, and a 2026 follow-on, **CVE-2026-27795**, shows that even a *patched* SSRF boundary (`prevent_outside=True`) was bypassed via automatic redirect-following, requiring a second fix (disabling auto-redirects, re-validating the `Location` header on every hop) ([SentinelOne](https://www.sentinelone.com/vulnerability-database/cve-2024-0243/); [Mondoo](https://mondoo.com/vulnerability-intelligence/vulnerability/CVE-2026-27795)). OWASP's core recommendation is to prefer **allowlisting over denylisting** ("deny-lists are bypass-prone"), validate the DNS-resolved IP (to defeat DNS-rebinding bypasses), disable automatic redirect-following, route all such fetches through an isolated egress proxy with no route to internal banking systems, and harden cloud metadata access (IMDSv2) ([OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)). Any version of Option 2 that Mashreq builds — even a scoped one — must be built to this standard from day one, not retrofitted after an incident.

Even setting security aside, Option 2 degrades on its own terms over time. Web and legal-citation research both document substantial **link rot**: Pew Research's 2024 study of roughly 500,000 government webpages found **about 21% had at least one broken link**, with decay compounding by age (38% of 2013-era pages gone by 2023, vs. 8% of 2023-era pages) ([Pew Research Center](https://pewresearch.org/wp-content/uploads/sites/20/2024/05/pl_2024.05.17_link-rot_report.pdf)), and a Harvard Law Review study found **more than 70% of law-journal URL citations** affected by "reference rot" — the link still resolves, but no longer shows the originally cited content ([Harvard Law Review](https://harvardlawreview.org/2014/10/perma-scoping-and-addressing-the-problem-of-link-and-reference-rot-in-legal-citations/)). Reference rot is the more dangerous variant for a compliance system specifically because it is silent: an automated dead-link check won't catch it, so a crawl-once-and-index pipeline can serve superseded SWIFT or regulatory guidance as if current, with no signal that anything changed, unless content-hash-based change detection or scheduled re-crawling is explicitly built in.

## Citation-only fails the audit bar compliance RAG is held to

Option 1 looks safe by comparison — no crawling, no SSRF surface, no stale indexed copies — but the compliance-RAG and legal-tech literature converges on treating a bare citation/pointer as **insufficient for audit purposes on its own**. The recurring argument is that a citation shows what the model mentioned, not the retrieval path: which documents were actually available, which version was in force, and whether a human or the model resolved an ambiguity ([Elliptic](https://www.elliptic.co/corpus/gen-3629/knowledge-based-software-assistant/retrieval-augmented-generation-rag-patterns-for-compliance-grade-knowledge-based-software-assistants.html)). Practitioner guidance for regulatory-content AI workflows converges on a fairly consistent minimum **provenance schema** per ingested/cited source: an immutable raw snapshot, a parsed text version, a content hash, a retrieval timestamp (`retrieved_at`), the source's own publication/effective date, and a version signal (ETag/Last-Modified or revision marker) — precisely so an auditor can later answer "what did we rely on, and was it in force on that date?" ([Promise Legal](https://blog.promise.legal/building-reliable-ai-workflows-law-firms-government-regulatory-content/)). A citation-only design that lets the user "manually follow the link" cannot reconstruct this after the fact: if the external page has since changed or disappeared (a near-one-in-five chance within a decade, per the Pew figures above), the system has no record of what the citation actually pointed to when the answer was generated.

This is also where "citation freshness" shows up as a named, first-order design concern rather than an afterthought. A compliance-RAG vendor pattern explicitly recommends **time-bounded retrieval** — serving the policy/sanctions-list version "effective on that date," not always the newest version — specifically to avoid silently applying today's rules to a historical decision, a failure mode named **"policy drift"** ([Elliptic](https://www.elliptic.co/corpus/gen-3629/knowledge-based-software-assistant/retrieval-augmented-generation-rag-patterns-for-compliance-grade-knowledge-based-software-assistants.html)). The same source frames the honest trade-off Mashreq is facing: snapshot-first retrieval favors auditability and reproducibility but risks staleness between regulatory updates, while live fetching favors currency but risks pulling unofficial or mid-update pages and makes answers non-reproducible (same question, different answer on different days) — and recommends a hybrid where versioned snapshots are the system of record, live fetching (restricted to an allowlist of official domains) is used only to *check* whether a snapshot is stale, and ambiguous or changed-rule cases are routed to human review rather than resolved silently by the model. It is worth being precise about the regulatory baseline here: **no financial or AI regulator has published binding text specifically naming "RAG," "hyperlink handling," or "citation freshness."** The closest adopted anchors are the EU AI Act's Article 12 logging obligations for high-risk systems (general traceability, not RAG-specific, and not yet in force — 2 December 2027 / 2 August 2028 per secondary commentary) and SR 11-7-style model risk management expectations, which practitioner commentary argues should extend to GenAI/RAG pipelines on the theory that "you cannot independently challenge an output you cannot trace back to its sources" ([EU AI Act Art. 12](https://ai-act-service-desk.ec.europa.eu/en/ai-act/article-12); [industry MRM commentary](https://www.rapiddata.com/insights/news/genai-model-risk-management)). In other words: the provenance discipline described here is industry best practice converging from multiple independent sources, not yet a codified regulator checklist — which argues for building it proactively rather than waiting for an examiner to ask for it.

| | Option 1: citation-only | Option 2: crawl everything | Middle ground: reference-node + governed fetch |
|---|---|---|---|
| SSRF / network risk | None | High — demonstrated CVEs in mainstream tooling | Low if fetch is allowlisted + IP-validated |
| Audit/provenance | Weak — no record of what the link showed | Strong if snapshot+hash retained, but costly at scale | Strong — pointer + optional snapshot, scoped to what's actually used |
| Staleness exposure | Invisible to the system; user may click a dead/changed link | Must be actively managed (hash/ETag re-checks) or silently goes stale | Managed per-domain, only for the small set of links worth tracking |
| Engineering cost | Minimal | High (crawler infra, depth/allowlist controls, re-crawl scheduling) | Moderate (link extraction + metadata graph; fetch only on demand) |
| Matches ~5,220-page compliance corpus scale | Yes, but weak for audit | Poor — external link graph is effectively unbounded | Yes — scoped to in-corpus links plus a short allowlist |

## The documented middle ground: metadata pointer, not crawled content

A named alternative to the crawl-vs-ignore binary exists across both industry and academic sources, and it converges on the same mechanical shape regardless of vendor: **extract the hyperlink (anchor text, target URL/ID, source chunk) at ingestion time and store it as structured metadata or a typed graph edge — not as fetched content — then resolve it, conditionally, only at query time.** DataStax's RAGStack "Knowledge/Graph Store" attaches a `links` metadata field to each document node via an `HtmlLinkExtractor`, with a tunable retrieval `depth` parameter (0 = vector-only, 1 = vector search plus one hop of edge traversal) ([DataStax ragstack-ai-knowledge-store](https://github.com/datastax/ragstack-ai/blob/main/libs/knowledge-store/README.md)). LlamaIndex's `PropertyGraphIndex` offers the same shape with an `ImplicitPathExtractor` that builds relations purely from a document's own existing structure — no LLM required, since the link already exists structurally — and a `path_depth` parameter controlling how many hops are followed *after* an initial vector-similarity hit, so expansion is anchored to relevance rather than a blanket graph walk ([LlamaIndex docs](https://docs.llamaindex.ai/en/latest/module_guides/indexing/lpg_index_guide)). Contextual AI's engineering write-up names the underlying failure mode directly — a chunk says "Refer to Section 4.2.1," but the referenced text doesn't match the user's query well enough to surface via plain semantic search — and solves it with a **secondary "aliases" metadata index**, queried only when the retrieval agent decides a reference matters; on their internal compliance benchmark this beat content-only retrieval (75.4% vs. 67.8% accuracy under a 5-turn limit) while using fewer tool calls and less latency ([Contextual AI](https://contextual.ai/blog/an-agentic-alternative-to-graphrag)). A 2026 paper, **LARAG** ("Link-Aware Retrieval Strategy for RAG Systems in Hyperlinked Technical Documentation"), is purpose-built for almost exactly Mashreq's scenario: it stores author-defined hyperlinks as chunk-level metadata rather than materializing a separate graph, runs ordinary semantic search first, then traverses outgoing links on-the-fly with a depth-limited, reranked, deduplicated expansion (parameters `n_links`, `depth`, `top_m`, with a global visited-set to prevent cycles) ([arXiv 2605.07517](https://arxiv.org/pdf/2605.07517)). Separately, in the legal/regulatory domain specifically, multiple 2025–2026 systems (an Indian legal assistant, a New Mexico legal-RAG system) build citation graphs in Neo4j with typed edges ("cites," "amends," "shares-principle") and an LLM/router deciding when to traverse vs. stay in flat vector retrieval, reporting meaningfully higher pass rates for the hybrid approach (70% vs. 37.5% in one self-evaluated benchmark) — though a COLIEE 2026 entry's sharp drop from cross-validation F1 (0.311) to test F1 (0.177) is an explicit, documented caution that citation-graph gains do not reliably generalize to held-out data, so any such design needs its own evaluation rather than an assumed win ([arXiv 2602.23371](https://arxiv.org/pdf/2602.23371); [COLIEE 2026 entry](https://papers.cool/arxiv/2609.26237)).

Two caveats are important for setting expectations correctly with the team. First, **Microsoft's GraphRAG is not this pattern** — its graph edges are LLM-inferred semantic relationships extracted from text, built regardless of whether the source document contains literal hyperlinks, and it is comparatively expensive to build and update; Contextual AI's own critique argues its "heuristic overload" and costly recomputation on document change produced diminishing returns relative to cost and latency in their ablations ([Contextual AI](https://contextual.ai/blog/an-agentic-alternative-to-graphrag)). If Mashreq wants hyperlink-structured edges specifically, GraphRAG-style LLM entity extraction is the wrong tool; the ImplicitPathExtractor/HtmlLinkExtractor-style "parse the document's own link markup" approach is the right one, and it's cheaper. Second, neither LARAG nor Contextual AI's aliases pattern was documented specifically for genuinely **external** off-corpus links (both are about internal "see Section X" cross-references) — this is a real gap in the literature relative to Mashreq's SWIFT/FATF/CBUAE use case, meaning the external-link half of the design (what to do when the reference-node points outside the corpus) is where Mashreq will need to extend the pattern rather than copy it wholesale.

## Tooling reality: link extraction is inconsistent across PDF parsers

Implementing the metadata/reference-node pattern requires reliably pulling hyperlink URLs out of the source documents first, and here the tooling landscape has a hard split that directly affects Mashreq's 108-PDF-heavy corpus. Tools built around **HTML** have mature, structured link metadata essentially for free: Unstructured.io's official docs confirm `link_urls`, `link_texts`, and `link_start_indexes` fields for HTML (and partially PDF) content ([Unstructured docs](https://docs.unstructured.io/open-source/concepts/document-elements)). Tools centered on **PDF**, by contrast, largely do not expose link targets without extra work. **Azure AI Document Intelligence** — a candidate for Mashreq given the likely Azure stack — has Microsoft's own Q&A moderators confirming twice (2023 as Form Recognizer, again in 2025) that it "does not natively extract or separate the URLs from the hyperlink text," with the suggested workaround being regex or a dedicated PDF library joined to the OCR output ([Microsoft Q&A](https://learn.microsoft.com/en-us/answers/a/2002080)). **PyMuPDF4LLM** (common for PDF→Markdown pipelines) has hyperlink extraction confirmed unsupported by a maintainer, who also notes that many PDF link annotations are invisible overlay rectangles rather than aligned with visible anchor text — meaning naive text-to-link alignment is unreliable and a geometry/position-based join is often necessary ([MuPDF forum](https://forum.mupdf.com/t/issue-hyperlink-extraction-from-pdf-to-markdown-is-not-working/263)). Default LangChain (`PyPDFLoader`) and, per community reports, default LlamaIndex PDF loaders similarly drop link annotations, exposing only page/source metadata. What *does* work directly: **pdfplumber** exposes a `.hyperlinks` property per page (PDF spec §8.4 Link annotations), and **PyMuPDF**'s `page.get_links()`/`page.links()` returns link annotation dictionaries with URI targets ([pdfplumber README](https://cdn.jsdelivr.net/gh/jsvine/pdfplumber@stable/README.md); [PyMuPDF tutorial](https://pymupdftest.readthedocs.io/en/stable/tutorial.html)). For the 5 DOCX files, dedicated converters (Deepset's `DOCXToDocument`, ContextGem) already productize "preserve link text and target URL, render inline as Markdown `[text](url)`" as a configurable option, so DOCX is comparatively low-risk. Practically, this means whatever platform Mashreq standardizes on for parsing (Azure DI, Docling, Unstructured), the team should plan a **dedicated link-extraction pass using pdfplumber or PyMuPDF over the PDF set**, joining extracted link annotations back to the parsed text by page/position, rather than assuming the primary document-intelligence tool will surface this metadata on its own — this is a known, recurring gap across Azure DI, PyMuPDF4LLM, and default LangChain/LlamaIndex loaders alike, not a Mashreq-specific integration bug.

## A practical middle-ground design for TADA Studio

Synthesizing the above into something implementable: at ingestion time, run a link-extraction pass (PyMuPDF/pdfplumber for the 108 PDFs; native DOCX converter options for the 5 DOCX; a comparable PPTX hyperlink-relationship parse for the single deck) that captures, per link, the anchor text, target URL, source document ID, page/slide number, and surrounding chunk text — this becomes a `REFERENCES` edge (chunk → external-authority placeholder node, or chunk → internal cross-reference) in a lightweight graph/metadata layer, mirroring the DataStax/LlamaIndex pattern, with **no content fetched at this stage**. Retrieval then runs ordinary vector search first; only when a retrieved chunk's reference metadata is judged relevant (either via a `path_depth=1`-style bounded traversal or an agent explicitly recognizing a "see also" pattern, as in Contextual AI's aliases design) does the system surface the pointer — as a citation, not auto-expanded inline content — to the user. This alone satisfies a strong version of "Option 1 done well": the user sees the link, but the system has also captured structured, queryable provenance about every reference in the corpus, which an audit can enumerate even without ever fetching a single external page.

The decision the team actually needs to make is narrower than "crawl or don't": **for which specific domains, if any, is it worth maintaining a governed, periodically-refreshed snapshot?** Given the corpus description (SWIFT standards pages, other regulatory bodies, internal cross-references), a defensible scope is a **short, explicitly maintained allowlist** — official SWIFT, CBUAE, FATF, and equivalent regulator domains only, explicitly excluding the open web — fetched through an isolated egress proxy with no route to internal banking systems, with the fetcher validating the DNS-resolved IP (not just hostname) before connecting and auto-redirect-following disabled, per OWASP's SSRF guidance and in direct response to the CVE-2026-27795 redirect-bypass pattern. For this allowlisted set only, apply the documented freshness machinery: a content hash (not a timestamp, since `Last-Modified` headers are not reliably trustworthy) computed at first fetch and compared on each scheduled re-check, conditional-GET (`ETag`/`If-Modified-Since`) to cheaply detect "unchanged," and a superseded-but-retained version history so that a historical answer can be reproduced against the regulation as it stood on the date a decision was made — directly addressing the "policy drift" risk named in compliance-RAG literature. Everything outside that short allowlist — the long tail of incidental links a 5,220-page corpus will inevitably contain — stays reference-node-only: captured, searchable, cited, never auto-fetched. This keeps the blast radius of any fetching capability small and auditable (a handful of known-good domains, not an open-ended crawl), keeps the provenance schema (retrieval timestamp, hash, effective date, version ID) tractable to actually maintain, and gives Sachin, Vishal, Ziye, and Vipul a design that is defensible to an examiner without requiring Mashreq to operate general-purpose web-crawling infrastructure inside the bank's network.

## Conclusion

The research reframes the team's decision: this was never really a binary between "just show the link" and "crawl the internet," and treating it that way concedes too much to each option's documented worst case — Option 1's audit gap and Option 2's SSRF/crawler-trap/staleness-maintenance burden. The reference-node/graph pattern is not a novel compromise invented for this report; it is independently converged-on infrastructure (LangChain, LlamaIndex, DataStax, LARAG, Contextual AI) precisely because "capture the reference, defer the fetch" solves the retrieval problem (surfacing a cross-reference chunk that wouldn't otherwise match the query) without inheriting either extreme's failure mode. The one genuinely open design choice left for Mashreq's engineering team is the allowlist scope and refresh cadence for the small set of external domains worth actually fetching — a scoping decision, with known mitigations (OWASP SSRF controls, hash-based freshness checks, versioned snapshots), rather than an unsolved architecture problem. The team should also go in clear-eyed that no regulator has yet written rules naming RAG or hyperlink handling specifically; the provenance discipline recommended here is the industry's best current answer to "what will an examiner ask for," not a checklist copied from an existing CBUAE or EU AI Act requirement — which argues for building the audit trail generously now, since it is far cheaper to retain than to reconstruct after the fact.
